- REST base `/wp-json/wp/v2/research`;

## Authority invariant

```text
GitHub publication contracts = scientific authority
WordPress                  = editorial and visibility layer
```

WordPress cannot elevate a review status, manufacture a DOI, change DOI scope, close QMD G2/G6, or turn a negative external benchmark into a positive result. Publishing a WordPress record means only that its page is publicly visible.

## Import safety

The synchronizer is local-only and fail-closed:

1. verify bundled manifest and SHA-256;
2. verify byte-identical bundled registry/model files through the pinned manifest hashes, then validate the supported schema versions and the structural, identity, status, path, DOI/null, and reciprocal-companion invariants used at runtime;
3. acquire a connection-owned MySQL/MariaDB advisory lock and fence diagnostic, journal, and state transitions to the owning database connection;
4. reject an unresolved prior journal;
5. scan all post statuses for duplicate work IDs, archive conflicts, and canonical-slug collisions;
6. build a complete plan before the first research-record write;
7. persist existing-record snapshots and all create intents before the first write; every new row carries a token marker in the same post-row insert until its ID is durably journaled;
8. create only drafts and update only importer-owned fields;
9. verify every stored record and all global uniqueness invariants;
10. rollback on failure, verify the restored slug/meta snapshot and prior state, and hard-delete a new draft only when its full conservative post/meta/relationship fingerprint proves that no editor or hook added data; otherwise retain the record and journal for operator review.

Repeat synchronization against unchanged input does not call `wp_insert_post()` or `wp_update_post()` and therefore does not create post revisions. Editorial content, excerpt, thumbnail, author, status, media, and layout are never overwritten on update. Removed registry entries become diagnostics-only orphans; they are never deleted automatically.

The non-MySQL development fallback uses an add-only option mutex and intentionally has no automatic stale-lock takeover. It is suitable for clean-run Playground validation but fails closed after a crashed request; the documented automatic crash-recovery guarantee is tied to the standard WordPress MySQL/MariaDB backend.

## Write protection

- machine meta is hidden from the ordinary custom-fields UI;
- standard meta REST writes are denied by `auth_callback`;
- metadata add/update/delete filters deny non-importer writes;
- metadata-by-ID update/delete filters close the alternate core metadata mutation path, including key renames;
- `rest_pre_insert_research_output` returns 403 when a request attempts to submit Observer machine meta;
- derived REST fields have no `update_callback`;
- import requires `manage_observer_registry`; wp-admin import is POST-only and nonce checked;
- manual post creation is disabled;
- deletion of a registry record requires the registry-management capability.

## Output safety

- badge labels and CSS tones come from closed code maps;
- links use context-specific URL escaping;
- claim and reproducibility URLs use the exact pinned 40-character source commit, never mutable `main`;
- JSON-LD uses `wp_json_encode()` with `JSON_HEX_TAG`, `JSON_HEX_AMP`, `JSON_HEX_APOS`, and `JSON_HEX_QUOT`;
- no front-end or import-time external HTTP requests exist in P1.6;
- uninstall removes operational options/capability only and preserves all research posts and metadata.

## Explicit non-claims and next gate

The native Playground database smoke test establishes the core import/read-only contract, but the target hosting tier, staging instance, theme, cache, and installed SEO plugins are not yet fixed. A target-staging compatibility run therefore remains the next deployment gate. Until that gate is complete, this package is a validated implementation candidate, not a claim that the live site has been migrated.
